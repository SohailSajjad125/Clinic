# ClinicOS security audit

Scope: backend API, web app, marketing website, database, dependencies and packaging. Date of this pass: October 2026.
"Verified" means a test or a live probe ran and passed; the test name or command is given. This is a **self-audit**, not an independent penetration test (see the last section).

## Checklist

| # | Item | Result | How it was verified |
|---|---|---|---|
| 1 | **Hide API keys** | Pass | Secret-pattern scan of all source, config and docs found nothing. Keys (`GROQ_API_KEY`, `TWILIO_*`, `SMTP_*`, `JWT_SECRET`) are read only on the server from the environment; no `NEXT_PUBLIC_*` variable holds a secret (they are only URLs). `.env` is git-ignored and excluded from the package; only `.env.example` ships, with empty values. The assistant calls Groq from the backend, so the browser never sees the key. |
| 2 | **Check env variables** | Pass | `ENVIRONMENT` defaults to `production` (fail closed). In production the API **refuses to start** with a weak/predictable `JWT_SECRET`, SQLite, the default DB password, `*` or `localhost` CORS origins, non-HTTPS origins, or a non-HTTPS `APP_URL`. `test_production_refuses_unsafe_configuration_and_hides_docs` proves the process exits with the error. |
| 3 | **Protect admin routes** | Pass | Every `/admin` route needs a platform-admin session. `test_admin_routes_reject_every_non_superadmin` tries all of them as owner, doctor, receptionist, nurse and patient (all 403). A platform admin cannot be created through the API (`test_superadmin_cannot_be_created_through_the_api`, including a mass-assignment attempt); only the CLI creates one. The web app also redirects non-admins away from `/admin`. |
| 4 | **Proper authentication** | Pass, one residual risk | bcrypt cost 12; short-lived access tokens; rotating refresh tokens kept per device server-side (replaying an old one revokes the session); the session, membership and clinic status are re-checked in the database on every request; tokens must carry `exp`, `iat`, `sub`, `sid`, `type`; algorithm pinned. 5 wrong passwords lock the account for 15 minutes. Password reset and email-verification links are single-use, expire, and are stored hashed. Passwords set by someone else (staff, patients) **must be changed on first login** before anything else works. Verified by `test_token_forgery_and_tampering_rejected` (expired, wrong key, `alg=none`, missing claims, wrong type, unknown session, bad signature), `test_sessions_logout_refresh_reuse_and_password_flows`, `test_lockout_after_failed_logins`, and a real-browser run of the forced password change. **Residual:** tokens live in the browser's `localStorage`, so an XSS bug would expose them (mitigated by the nonce CSP and React escaping; moving the refresh token to an httpOnly cookie is the recommended next step). No 2FA. |
| 5 | **Access control** | Pass | Every query is scoped to the clinic; roles are enforced per endpoint. `test_cross_clinic_access_is_impossible_for_every_object_type` makes a rival clinic attempt 40+ read, edit, delete, restore and purge calls on patients, appointments, consultations, invoices, documents, inventory, services, locations, templates, staff, notifications, chat and trash (all 403/404; data unchanged). `test_role_matrix` checks which roles may call key endpoints. `test_patient_and_superadmin_tokens_cannot_use_staff_endpoints` sweeps all staff endpoints. |
| 6 | **Sanitize forms** | Pass | Every request body inherits a base model that strips control characters (a NUL byte crashes PostgreSQL) and surrounding whitespace; field lengths, enums, e-mail format, number ranges, working-hours format, vitals size and search length are validated server-side. Password rules: 8-72 bytes, no common passwords, no all-digit/low-variety, must not contain the e-mail name. `test_password_policy_and_input_sanitising`. Client-side HTML validation is only a convenience. |
| 7 | **XSS protection** | Pass | React escapes all rendered values; the only `dangerouslySetInnerHTML` uses are three static scripts (theme switch, JSON-LD with `<` escaped). The web app sends a **per-request nonce CSP** (`script-src 'self' 'nonce-…' 'strict-dynamic'`, no `unsafe-inline` for scripts, `object-src 'none'`, `frame-ancestors 'none'`). Uploads of active content (SVG, HTML, EXE) are refused; downloads are `attachment` + `nosniff`; PDFs escape user text. Verified by a **real-browser test** that stores `<img onerror=…><script>…</script>` as a patient name: it renders as text and never runs (also in the Ctrl+K palette), plus `test_html_in_data_is_inert_in_pdfs_and_json`. |
| 8 | **Rate limiting** | Pass (single-server) | Global per-IP limit; stricter limits on sign-in, sign-up, password reset, public forms; per-**user** limits on the assistant, chat, uploads and portal messages; request body limits (1 MB JSON, 12 MB uploads, also when the body is chunked). `test_rate_limits_ip_user_and_global`, `test_request_size_limits`. **Residual:** counters are in memory; with more than one server use Redis or your proxy/WAF. Behind a proxy the limiter sees the proxy's IP unless the proxy forwards the client address (see DEPLOYMENT.md). |
| 9 | **Secure API endpoints** | Pass | `test_every_non_public_endpoint_requires_a_valid_session` calls **every operation in the OpenAPI schema (90+)** without a token and requires 401 on all except the nine intentionally public ones. Validation errors no longer echo submitted values (they previously could echo a password); unexpected errors return a generic message with no stack trace. Only GET/POST/PATCH/DELETE are allowed. |
| 10 | **CORS settings** | Pass | Exact origins from `CORS_ORIGINS`; credentials disabled (bearer tokens, no cookies); only the needed methods and the `Authorization`/`Content-Type` headers. Live probe: an `evil.example` origin gets no `Access-Control-Allow-Origin`; the configured origin does. |
| 11 | **Security headers** | Pass | API: `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `Cache-Control: no-store`, CSP `default-src 'none'`, HSTS in production, also on error responses. Web app and website: CSP, `nosniff`, frame denial, referrer and permissions policies, COOP, HSTS; `X-Powered-By` removed. Real-browser header assertions run on both frontends. |
| 12 | **Debug mode off** | Pass | FastAPI `debug=False`; `/docs`, `/redoc`, `/openapi.json` return 404 in production (live probe); Next.js runs a production build; no source maps are shipped (0 found); unhandled errors are logged server-side only. |
| 13 | **Update dependencies** | Pass | `pip-audit`: no known vulnerabilities; all pinned runtime packages are at the latest release. `npm audit`: 2 findings in Next.js's bundled PostCSS were fixed by upgrading Next 15 to **16.3.8**; both apps now report 0 vulnerabilities and were rebuilt and re-tested. Deliberately **not** upgraded (no vulnerabilities, breaking major versions): framer-motion 14, lucide-react 1.x, recharts 3, tailwindcss 4. |
| 14 | **Remove unused packages** | Pass | `depcheck`: no unused runtime dependencies in either frontend (it flags only the Tailwind/PostCSS build tools, which are used). Python: every import is declared and every declared runtime package is imported. Test-only tools moved to `requirements-dev.txt`. The unused Redis service was removed from `docker-compose.yml`. |
| 15 | **Check exposed files** | Pass | Live probes in production mode returned 404 for `/.env`, `/.git/config`, source files, `package.json`, `next.config.js`, `node_modules`, path traversal (`/../etc/passwd`), `/storage` on the API and both frontends. No `.env`, key or certificate files are in the package (`.gitignore` added). Uploaded files live outside any served path, have random names and mode 0600, and are only served through authenticated endpoints. |
| 16 | **Secure database** | Pass, deployment steps needed | All queries go through SQLAlchemy with bound parameters; the only raw SQL is `select 1`. Search uses escaped `LIKE`. CHECK constraints enforce non-negative stock and valid invoice amounts **in the database itself** (verified by trying to insert bad rows). `scripts/create_db_roles.sql` creates a least-privilege application role; verified on PostgreSQL: the app role can read and write rows but is **denied** DROP, ALTER, CREATE, CREATE ROLE and `pg_shadow`, and the whole API (register, patient, appointment, analytics) worked under it. The dev database listens on `127.0.0.1` only, with a required password. Migrations rebuild the schema from scratch with no drift. **You must:** use TLS (`sslmode=require`), encryption at rest and backups at your host. |
| 17 | **Hash passwords** | Pass | bcrypt, cost 12, unique salt (`test_passwords_and_tokens_are_hashed_and_never_returned` checks the stored format). Reset/verify tokens are stored as SHA-256 hashes. No endpoint returns a hash. Login does a dummy hash for unknown e-mails to even out timing. |
| 18 | **Full security audit** | This document | 42 automated tests pass on PostgreSQL (15 of them are the security tests above), plus 18 real-browser checks, bandit (no findings at any severity), pip-audit and npm audit (0 vulnerabilities), live exposure probes and the least-privilege database test. |

## Problems found during this audit (all fixed)
1. Validation errors echoed back the submitted values, including passwords.
2. 500 error responses carried no security headers (the framework's outer error layer bypassed them).
3. CORS allowed every method and header, with credentials enabled.
4. No global rate limit, no per-user limits, no request-size limits.
5. Owners chose staff and patient passwords and kept knowing them; now forced to change on first login.
6. Weak passwords ("password123") were accepted.
7. A NUL character in any text field would have crashed PostgreSQL with a 500.
8. Working-hours and vitals accepted arbitrary shapes and sizes.
9. API docs and a production start with weak configuration were possible.
10. Next.js bundled a vulnerable PostCSS (fixed by upgrading Next).
11. The web app's CSP did not exist; scripts were not nonce-protected.
12. Dev database used a fixed weak password, was exposed on all interfaces, and an unused Redis was exposed.
13. The error message for a rejected password was generic; it now says why (found by the browser test).

## Residual risks and what this audit does not cover
- **Tokens in localStorage** (see item 4). Next step: httpOnly refresh cookie plus CSRF protection.
- **No two-factor authentication**, no account-recovery review process, no device/IP anomaly alerts.
- **Rate limits are per process** (item 8). **Registration reveals whether an e-mail exists** (409), a deliberate usability trade-off protected only by rate limiting.
- **Not independently tested:** no third-party penetration test, no fuzzing, no load test, no review of your hosting, TLS, firewall or secrets management. The Twilio and live Groq integrations were not exercised for real. Patient data sent to Groq by the assistant is governed by Groq's terms.
- **Compliance:** nothing here makes the product HIPAA/GDPR compliant; that needs a legal and organisational assessment.
- Privacy policy and terms are drafts.

# Addendum: second pass after the admin, notifications, doctor, patient-signup and Groq work

Re-checked against the same 18 items. Result: still pass; the new features were added with these controls.

| Area | What was added / verified |
|---|---|
| Admin routes | All new `/admin/*` operations (settings, audit, users, clinic detail, outbound log, sign-up chart, notifications) are covered by the route sweep (129 operations in the API are called without a token and only the 11 intentionally public ones answer) and by the "every role except platform admin gets 403" test. Admin accounts cannot disable each other. |
| API keys and secrets | The Groq key and other secrets set in the admin panel are encrypted (Fernet) before storage, never returned to any browser (only "…6789"), never written to the audit log (setting names only), and blank means "leave unchanged". Test: `test_groq_key_model_and_settings_are_managed_by_the_admin_and_stored_encrypted`. |
| SSRF | The Groq base URL must be `https://` and may not point at localhost, private, link-local or reserved addresses; model names are restricted to safe characters. A compromised admin cannot aim the assistant at internal services by that route. (Domains that resolve to private IPs are not checked.) |
| Notifications and dots | Every notification is created per recipient and scoped by role, clinic and user: patients never receive staff events, staff never receive other clinics' events, chat events go to staff only. Tests assert who does and does not get each dot (for example the nurse gets none for appointment requests, the doctor none for new patients). Opening a feature clears only that person's dot. |
| Patient self sign-up | New accounts always create a **new** patient record; they are never auto-linked to an existing record by e-mail (that would let anyone claim another person's chart). Staff e-mails cannot be used. Clinics can hide themselves (hidden clinics answer 404, not "forbidden", so existence is not revealed), plan limits apply, and the platform admin can switch patient or clinic sign-ups off. Public directory returns only name, city, country and type. Staff and patient login pages are separate and refuse each other's accounts. |
| Doctors and booking | Doctors cannot create patients (server-enforced, not just hidden). Double-booking the same doctor and time is refused (409). Patient requests need staff approval before they count as bookings. Slot lists only expose free/taken, never who booked. |
| CORS | Browser testing found that the stricter CORS list blocked `PUT` (used by the admin settings editor). `PUT` is now allowed for exact configured origins only; the security test checks that `PUT` is allowed and `TRACE` is refused. |
| Dependencies | `pip-audit` found three known vulnerabilities in `cryptography 46.0.6` (the library that encrypts stored keys); upgraded to 50.0.2, re-audited clean. `npm audit`: 0 on both frontends. `bandit`: no findings. |
| Test totals | 52 backend tests on PostgreSQL (37 functional/platform + 15 security) and 2 real-browser suites (15 + 19 checks). |

Residual risks from the first audit still apply (tokens in localStorage, no 2FA, per-process rate limits, no independent penetration test). New: the Groq key can be read by anyone who can read both the database **and** the server environment (`SETTINGS_ENCRYPTION_KEY`/`JWT_SECRET`); keep them on separate systems. Messages sent to patients by e-mail/SMS/WhatsApp travel over third-party networks and may contain appointment details.

# Addendum 2: palette, chat clearing, audit scope and role-based settings

| Area | What was done / verified |
|---|---|
| Audit log scope | `GET /audit` is owner-only and filtered by the caller's clinic in the database query. Tests create a second clinic with its own activity and prove the two logs share no entries and never mention each other's people. The log now also records logins, patient self sign-up, appointment requests and cancellations by patients, patient messages, staff replies, and clearing a chat. Only action names and ids are stored (no message text, no personal data). |
| Clear chat | Implemented as a per-person cut-off time, not a deletion, so it cannot affect anyone else's history. Tests prove the other staff, the patient and the clinic keep the full conversation, that new messages still arrive, that unread counts and red dots ignore cleared messages, and that other roles cannot call the wrong clear endpoint (403). |
| Role-based Settings | Hidden in the interface by role, and a typed-in address cannot reveal a hidden tab. The server independently enforces who may change clinic settings, services, templates, locations and plan data (owner-only), so the interface is convenience, not the control. |
| Pop-up forms | Fixed a usability bug: dragging a scroll bar was treated as a click outside the form and closed it, losing what had been typed. The form now scrolls inside its own box and only closes on a deliberate click on the dimmed area. |
| Doctors and nurses and passwords | By request, the Security tab (change password, signed-in devices) is hidden for doctors and nurses. They can still use "Forgot your password?" on the login page, and they must change a temporary password at first login, but they cannot review or sign out their own devices from the app. The owner can disable a user from the platform admin, and the clinic owner can remove staff. Consider re-enabling a password-only Security tab for these roles. |
| Colours | The palette change touched every screen. Status colours come from the brand guide; text on coloured fills uses a dark ink chosen for contrast (white on the guide's gold would fail accessibility at body size). |
| Scans after the changes | `bandit`: no findings. `pip-audit`: none. `npm audit`: 0 on both frontends. `depcheck`: no unused packages. 55 backend tests pass on PostgreSQL and 3 browser suites (15, 19 and 10 checks) pass. |
